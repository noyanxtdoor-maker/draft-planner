3. EXACT ROOT CAUSE (before this fix)
--------------------------------------------------------------------------------
- home_screen.dart read `nextTempleVisitProvider.asData?.value` and rendered
  the Temple card secondary line purely from null-ness:
    non-null -> 'Next Visit: <date>'; null -> 'Set Schedule'.
- That collapsed two distinct semantic states into one visual state:
    A. unresolved/loading (first-ever read in flight)
    B. resolved true-null (confirmed no schedule)
- The first-ever read therefore rendered "Set Schedule" while merely loading
  (the cold-start half of the defect), and Home's pull-to-refresh invalidated
  the provider, re-creating the flash window on every reload (the 8.5/10.9s
  pattern from the owner recording).
- Verified empirically on the unfixed build with a staged/pending repository:
  during the first unresolved read the line DID render "Set Schedule"
  (deterministic RED).  During a refresh, Riverpod 3.3.2's copyWithPrevious
  already retained the prior value, so the refresh window did not flash on the
  current code; the explicit tri-state contract below makes retention a
  guaranteed, tested behavior rather than an implicit framework detail.

4. CHOSEN TRI-STATE IMPLEMENTATION
--------------------------------------------------------------------------------
lib/features/indicators/application/indicator_providers.dart
- Added:
    enum NextTempleVisitStatus { loading, ready, failure }
    final class NextTempleVisitState { status; value; hasConfirmedValue;
      isResolvedNull (ready && value == null) }
- Replaced `nextTempleVisitProvider` (FutureProvider<PlannerDate?>) with
  `nextTempleVisitControllerProvider` (NotifierProvider<NextTempleVisitController,
  NextTempleVisitState>) following the established HomeIndicatorController
  pattern in the same file:
  - build(): watches startupControllerProvider + plannerDateSourceProvider
    (same dependency contract as the old FutureProvider: re-read on resume
    date-source invalidation / startup readiness), subscribes to the
    repository change stream (calendar-event writes auto-refresh), schedules a
    microtask refresh, returns the loading state.
  - refresh(): retains the previous CONFIRMED value while the read is in
    flight (never fabricates a date), applies the newer resolved result
    immediately on arrival (including a newer true-null -> Set Schedule),
    generation-guards against out-of-order completions, and on failure
    retains the previous value (failure never claims "no schedule").
- State semantics:
    loading (no confirmed value)  -> Home renders NEUTRAL empty secondary line
    ready + date                  -> 'Next Visit: <date>'
    ready + null                  -> 'Set Schedule' (keyed affordance active)
    failure + no previous         -> NEUTRAL (same as loading)

lib/features/startup/presentation/home_screen.dart
- Line ~90: `ref.watch(nextTempleVisitControllerProvider)` (the state, not
  .asData).  The state flows into _CanonicalHomePlan -> _CanonicalIndicatorGrid.
- Pull-to-refresh (RefreshIndicator onRefresh): replaced
  `ref.invalidate(nextTempleVisitProvider); await read(.future)` with
  `await ref.read(nextTempleVisitControllerProvider.notifier).refresh()`
  (the controller retains the prior line during the reload — the same
  retain-last-confirmed pattern already accepted for the Contact flicker fix).
- Temple card secondary line via new `_templeSecondaryLabel(...)`:
    value != null                -> 'Next Visit: ...'
    isResolvedNull               -> 'Set Schedule' + onSecondaryTap
    otherwise (loading/failure)  -> null label AND new `hideSecondaryLine`
                                    flag so the card renders NO secondary
                                    line (never the monthly ratio, never
                                    'Set Schedule') while unresolved.
- _goalCard / _IndicatorCard gained `hideSecondaryLine` (default false);
  only the Temple unresolved state sets it.
