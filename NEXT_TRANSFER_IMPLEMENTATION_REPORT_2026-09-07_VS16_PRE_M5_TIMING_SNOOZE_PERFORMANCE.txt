4. GATE A — TIMING / SNOOZE FORENSIC FINDINGS
======================================================================
Measured source-path evidence:

Normal reminder scheduling path before correction:
  FlutterLocalNotificationsGateway.schedule(request)
    -> cancel current plugin notification by platform ID
    -> WorkmanagerBackgroundWorkGateway.enqueueUnique(...)
    -> Workmanager.registerOneOffTask(... initialDelay: target-now)
    -> headless reminder runtime / ReminderReconciler
    -> FlutterLocalNotificationsGateway.showCanonicalReminder(...)
    -> plugin.show(...).

Source evidence:
  lib/core/notifications/flutter_local_notifications_gateway.dart scheduled
  every normal reminder through a WorkManager one-off task with `initialDelay`.
  It did not call a platform local-notification scheduler.

Snooze path before correction:
  notification Snooze action
    -> nextTransferReminderAction
    -> enqueueReminderSnooze unique WorkManager task
    -> runReminderRuntime
    -> ReminderReconciler computes accepted action + ten minutes
    -> same WorkManager one-off delivery path above.

Proven root cause:
  WorkManager one-off work is opportunistic. It is appropriate for durable
  recovery/reconciliation but is not a precise delivery clock. Routing normal
  reminders and Snooze re-fire through its `initialDelay` is an app-controlled
  design that permits the reported 30–45-second device-side jitter.

Not yet measured on a new corrected APK:
  - exact controlled source target, stable key, scheduledForUtc,
    nextEligibleAtUtc, platform ID, and source revision;
  - WorkManager database/runtime timestamps and result for a controlled item;
  - Android NotificationManager post timestamp and visible-arrival delta;
  - Snooze action timestamp, calculated +10-minute target, generation check,
    source eligibility at target, and channel alert behavior.

Therefore, this report distinguishes the source-proven latency cause from a
not-yet-completed physical before/after timing measurement.
