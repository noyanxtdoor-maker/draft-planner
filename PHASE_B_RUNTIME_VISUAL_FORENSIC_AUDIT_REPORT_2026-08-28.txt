B. RUNTIME TASK RENDER MAP
===============================================================================

1. Saved timed, non-recurring Task

  Planner provider/day projection
    -> `_PlannerScreenState._visibleTimelineTasks` (planner_screen.dart
       1677-1700; incomplete Tasks with dueMinute)
    -> `_TimedEventTimeline.tasks` (1450-1521, 3774-3905)
    -> `_taskFootprints` creates `task-footprint:<taskId>` with the frozen,
       presentation-only 15-minute end (4077-4107)
    -> `PlannerDisplayGeometry.resolve` for shared vertical geometry and
       `PlannerTimelineLayout.arrange` for logical collision lanes
       (4337-4352; planner_display_geometry.dart 113-258)
    -> `_positionedTimelineTask` (5122-5171)
    -> `_TimelineTaskBlock` (5969-6112).

  Runtime widget: separate Task renderer, not `_TimelineEventBlock` and not
  `PlannerEventBlockContentView`. A non-recurring Task receives a long-press
  move callback only when quick edit is enabled (5131-5135; 6028-6034). It
  has no resize callbacks or endpoint handles.

2. Saved timed recurring Task projection

  `PlannerTask.projectsOn` maps canonical recurrence arithmetic to the
  requested date (planner_task.dart 162-182), then follows the exact saved
  Task path above. `_positionedTimelineTask` computes `dragEnabled` only for
  `PlannerTaskRecurrence.none` (5131-5135); `_TimelineTaskBlock` presents the
  explicit recurring non-movable hint (6018-6020). It remains the separate
  Task renderer.

3. Eligible completed timed Task

  `_visibleTimelineTasks` includes `day.completedTasks` only when the completed
  Tasks filter is enabled (1685-1700). It then follows the same footprint,
  geometry, and `_TimelineTaskBlock` path. Completed status is a visibility
  decision, not a different visual component.

4. Task draft/provisional block

  `launchTaskCreation` starts `plannerTaskCreationDraftProvider`
  (task_creation.dart 33-79). The parent passes both a synthetic
  `task-draft:<id>` planner item (planner_screen.dart 1453-1460,
  3255-3279) and the Task draft value to `_TimedEventTimeline`. The timeline
  resolves its placement then calls `_positionedTimelineTaskDraft`
  (5173-5227). That function builds a synthetic `PlannerTask` and instantiates
  the SAME `_TimelineTaskBlock` as a saved Task (5201-5225).

  Saved and draft Tasks therefore share one Task-only primitive. They do not
  share the Event family's block primitive. Draft parity is parity with the
  legacy Task renderer, not parity with an Event-family Task design.

5. Narrow collision Task

  Task footprints are passed into the same layout input list as Events
  (4343-4352). `PlannerTimelineLayout.orderedByLanePriority` sorts Task
  presentation IDs before Events (planner_timeline_layout.dart 449-472), and
  `arrange` assigns collision columns from those logical intervals
  (211-324). The resulting width enters `_TimelineTaskBlock` through
  `_positionedTimelineTask` (5122-5169).

  `_TimelineTaskBlock` has a Task-specific narrow-width policy: under 120 px
  it removes the time; under 56 px it renders only the status badge; otherwise
  it renders title/status/time in a one-row LayoutBuilder (6040-6105). This
  prevents overflow, but it is not the Event block density policy.

6. Mixed Task/Event collision Task

  The same shared list and allocator are used. For a real logical overlap,
  Task IDs are left-prioritized by `orderedByLanePriority`, and later Events
  are constrained right of an overlapping Task by `arrange`
  (planner_timeline_layout.dart 251-284, especially 268-274). The Task itself
  is then painted by `_TimelineTaskBlock`; the Event is painted separately by
  `_TimelineEventBlock`. Thus collision placement is shared; visual shell and
  content are not.

Tap route

  `_TimelineTaskBlock.onTap`
    -> `_handleEventTap(footprint)` (5154)
    -> detects `task-footprint:` and resolves the real PlannerTask
       (4142-4152)
    -> parent `onTaskTap` uses `context.push('${RoutePaths.tasks}/${task.id}')`

    -> GoRouter `RouteNames.taskDetail` creates `TaskDetailScreen(taskId: ...)`

does not reuse this shell, its field components, its status-row composition,
or its map/contact components. That is the exact code reason the owner sees a
visually different legacy Task preview. No implemented Event-family Task
preview shell was found that is merely unwired; the required shared shell was
not created.

Tests do exercise direct status operations, but the audited Task timeline test

E. 15-MINUTE ZOOM / MINIMUM-HEIGHT FORENSICS
===============================================================================

Exact geometry chain:

  canonical start/end minutes
    -> `_taskFootprints` / real Event constructs PlannerCalendarItem
    -> `PlannerDisplayGeometry.resolve` (planner_display_geometry.dart 113)
    -> `_withDisplayInterval` (442-490)
    -> canonicalHeight = durationMinutes * (hourHeight / 60) (464-466)
    -> overviewByHeight = canonicalHeight < 28 (467-468)
    -> overviewByZoom = hourHeight <= 44 (469)
    -> if duration <= 45 and either condition is true, substitute the
       item’s start-hour to start-hour+60 DISPLAY interval (470-474)
    -> `PlannerTimelineGeometry.event` converts this substituted display
       interval into final top/height (194-200).

Logical lane assignment remains correct because it uses the pre-floor logical
list (131-143, 168-171). Display-lane packing then prevents enlarged bands from
painting over each other (301-440). The defect is neither logical duration nor
collision placement. It is the early display-interval substitution.

Important stale/contradictory documentation evidence:
`PlannerTimelineGeometry` describes exact duration geometry and no minimum
inflation (planner_timeline_layout.dart 119-127), but `PlannerDisplayGeometry`
later replaces qualifying short intervals with a 60-minute display interval.
Tests confirm the latter is the active runtime behavior.

Measured representative table (logical Flutter dp; no source change made)

  High/full inspection state: hourHeight = 120 px/hour
  pixels/minute = 2.0; the 28 px height threshold is not crossed.

  duration    raw height    floor active?    final height    visual minutes
  15 min      30 px         no               30 px           15 min
  30 min      60 px         no               60 px           30 min
  60 min      120 px        no               120 px          60 min

  Owner-failing intermediate band: hourHeight = 60 px/hour

Exact failure thresholds:
- 15 min becomes a one-hour display card whenever hourHeight < 112 because
  15 * hourHeight / 60 < 28. Thus it is floored at both 60 and 88 presets,
  and does not become proportional until 112 px/hour or greater.
- 30 min becomes a one-hour display card only below hourHeight 56, except
  compact mode at <=44 also forces overview.
- 60 min is outside the <=45-minute eligibility rule and remains factual.

The comparison above is precisely the reported physical signature: at a state
where hourHeight is in [56, 112), 15m looks one hour while 30m still looks 30m.
There is no separate `<=15` special case, 48/50/60 dp Task minimum, or legacy
50-minute persisted Task duration in the audited production paths. The source
does contain the distinct invisible Event touch target of 24 dp
(planner_screen.dart 3908-3913), but Tasks are placed at `placement.height`
without that visible/touch wrapper (5122-5169); it is not this visual defect.

Affected paths:
- Event 15/30/45-minute blocks: yes, shared `_withDisplayInterval`.
- Task 15-minute saved footprint: yes, it is in the shared resolver input.
- Task draft: yes, its synthetic 15-minute item is in the shared resolver.
- Event drafts: yes, when qualifying short PlannerCalendarItems.
- 60-minute items: no one-hour inflation because their final visual height is
  already one hour and they are outside the short-item condition.

I. RECOMMENDED CORRECTION SCOPE — READ-ONLY RECOMMENDATION
===============================================================================

Classification: 3. MIXED APPROACH.

It is not a one-line Task-only correction. The 15-minute error is a shared
display-geometry product-law error and should be corrected once, with Event,
Task-footprint, and draft coverage. The owner-visible Task parity failure is a
bounded presentation-layer completion: Task currently intentionally uses a
separate renderer and separate preview composition. A safe later pass should
reuse or introduce narrowly shared Event-family visual primitives while
retaining Task-specific domain/interactions. Do not convert Tasks into Events,
persist a duration, alter schema/migrations, or change reporting/collision
semantics.

Smallest safe approach:
1. Correct only the display-floor activation law in
   `PlannerDisplayGeometry._withDisplayInterval`, based on an explicit
   far-zoom threshold/curve that leaves the [56,112) intermediate band
   proportional for 15m and 30m.
2. Replace the Task-only block's visual internals with a constrained
   Event-family presentation primitive while preserving `_TimelineTaskBlock`
   as the Task interaction/domain wrapper.
3. Recompose `TaskDetailScreen` from shared detail-surface primitives (not
   from Event domain objects), retaining Task-specific fields/status actions.
